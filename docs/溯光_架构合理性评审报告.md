# 溯光 TracingLight · 架构合理性评审报告

> 评审日期：2026-09-04　|　评审方式：全量结构扫描 + 关键文件实读
> 对象基线：166 个 TS/TSX 文件 · 26,229 行 · 40 个 API 路由 · 35 个页面 · 60 依赖 + 18 开发依赖

---

## 一、总体架构印象

```
src/
├── app/            # Next.js App Router：student / teacher / admin 三端 + api/ 对称分层
├── components/ui   # shadcn/ui 组件库
├── lib/            # 纯函数与横切能力（objective-grading / password / server-auth / teacher-scope / api-fetch）
├── storage/database# db.ts(sql.js 运行时) + schema.ts(Drizzle) + seed.ts(种子数据)
└── hooks/ types/   # 较薄
```

**做对的事**：App Router 三端与 API 对称分层清晰；`lib/` 承载了可测试的纯函数（客观题批改引擎、密码工具均有单测）；`apiFetch` 统一了前端鉴权注入（27 个页面使用）；`teacher-scope.ts` 将教师数据归属收敛为共享工具，是本次安全治理的良好范式；Drizzle schema 类型安全；错误信息已脱敏。整体是一个**边界清楚、习惯统一的演示级应用**。

## 二、问题清单（按严重程度排序）

### 🔴 高严重度

#### P1-1 数据层为 sql.js 内存库，持久化是「定时全量快照」
- **位置**：`src/storage/database/db.ts`（30 秒 `setInterval` 全量 `saveToDisk`）
- **原因**：better-sqlite3 原生模块在当前环境安装失败，退化为纯 JS 的 sql.js。所有写操作只进内存，靠定时器/退出钩子把整个库（现已约 1MB）序列化落盘。
- **影响**：
  1. 强杀/断电最多丢 30 秒数据；
  2. 每次快照是全量写盘，数据量随使用增长，I/O 成本线性恶化；
  3. 进程崩溃时可能写入半截文件（无原子替换），存在整库损坏风险；
  4. 无 WAL/并发控制，多实例同时跑会互相覆盖 DB 文件（本次启动就遇到残留实例锁冲突）。
- **建议**：演示/答辩维持现状即可（已够用）；若要长期使用，**迁移 better-sqlite3 或 libsql** 是第一优先级——schema 层是 Drizzle，切换方言成本主要在安装环境而非代码。

#### P1-2 无 Service 层，业务逻辑散落在 40 个 route.ts 中，且存在「两套批改引擎」并行
- **位置**：`api/ai/grade`（规则引擎 + AI 分层批改）vs `api/ai/grade/batch`（内置另一套「长度比 + 词重合度」启发式打分）；批改→错题归档→掌握度更新这段三表联动逻辑在 grade/grade/batch/submit 各写了一遍。
- **原因**：迭代速度快，接口按页面需求各自生长，未及时沉淀。
- **影响**：
  1. **同一份答案走单题批改和批量批改会得到不同的分**——数据一致性风险直接可见；
  2. 横切逻辑（鉴权、归属、脱敏、错题归档）靠每个路由自觉，之前 IDOR 系统性漏修（H1~H6）正是这个结构的必然产物；
  3. 改一处规则要同步 N 个文件。
- **建议**：抽 `services/grading.service.ts`（统一走 objective-grading → AI 的分层管线）、`services/error-book.service.ts`（归档+掌握度 upsert）。批量接口直接复用单题管线，删除 batch 内置的简化引擎。

#### P1-3 权限校验靠「逐路由手写约定」，缺少框架级强制
- **位置**：37/40 路由有 `requireAuth`，但归属校验（`teacher-scope`）靠每处自觉 import；复审后又发现 `assignments` GET 下拉未过滤。
- **影响**：新增接口时极易再漏——这类问题历史上已发生两轮（学生端 IDOR → AI 端/教师端 H1~H6）。
- **建议**：封装高阶路由工厂，如 `withTeacher(handler)` / `withStudent(handler)`，在工厂内统一完成 鉴权→角色→数据范围注入（把 `myCourseIds/myStudentIds` 作为 context 传给 handler），让「忘记校验」从可能变为不可能；或至少在 Next `middleware.ts` 做角色粗筛 + ESLint 自定义规则扫描裸 `getDb()` 路由。

#### P1-4 密码哈希为 SHA-256 + 固定盐
- **位置**：`src/lib/password.ts`（代码注释已自知「演示用」）
- **影响**：SHA-256 可 GPU 高速穷举，固定盐使彩虹表可跨库复用；库文件 `data/tracinglight.db` 一旦泄露，弱口令几乎秒破。
- **建议**：换 bcrypt/argon2（纯 JS 的 `bcryptjs` 零原生依赖，当前环境可装）；登录时透明重哈希即可平滑迁移。

### 🟡 中严重度

#### P2-1 写路径几乎不用事务
- 全项目仅 2 处 `.transaction()`。批改流程 = gradingTask + errorBook + knowledgeMasteryLog 三表写入，中途失败（如某个字段格式异常抛错）会留下「有成绩无错题、掌握度未更新」的脏数据。
- **建议**：批改、提交、导入类多表写操作包进事务（sql.js 内存库无并发，事务零成本）。

#### P2-2 输入校验在边界处断裂
- zod 仅 1 处使用；API 层大量 `body.xxx` 直取 + `Number()` 裸转，PUT 接口曾出现 `...updates` 直接落库（exams 现已加白名单，但模式未推广）。
- **影响**：类型错误/NaN 落库、mass assignment 风险、500 而非 400。
- **建议**：为写接口统一 zod schema（`examSchema`、`assignmentSchema`…），`safeParse` 失败返回 400 + 字段级信息。

#### P2-3 测试覆盖与风险不成比例
- 现有 2 个测试文件（24 断言）全部针对纯函数；40 个路由的**鉴权/归属/参数边界零自动化测试**，全部靠人工 curl。
- **影响**：每次改动后回归验证成本高且易漏——这是本项目历史上最大的教训来源。
- **建议**：优先补「权限矩阵」集成测试：三角色 × 关键接口（analytics/exams/grade/errors）× （本人/越权/未登录）断言 200/403/401，一套用例即可锁住本次全部安全修复不回退。

#### P2-4 seed.ts 1018 行（155KB）硬编码数据与代码耦合
- 种子数据以字面量嵌在源码里，与 schema 同目录。每次调整数据都要动源码文件，diff 噪音大、无法按环境切换。
- **建议**：抽离为 `data/seed/*.json` + 一个通用 loader；或至少拆成 `seed/basic.ts`、`seed/academic.ts` 分主题文件。

#### P2-5 mock 数据残留不彻底
- `lib/mock-data-generator.ts`（575 行）仍被 `student/profile`、`recommend`、`study-plan` 三个路由引用（混合真实与模拟）。
- **影响**：演示时同一页面部分数据真实、部分随机，刷新即变，易被识破。
- **建议**：这三个接口的最后几项 mock 换成库内聚合；确认后删除该文件。

#### P2-6 前端无数据层抽象，页面组件过重
- 27 个页面各自 `useState + useEffect + apiFetch` 手写加载/错误/刷新；无 SWR/React Query 的缓存、去重、失效机制；多个页面 500~630 行（teacher/analytics 546 行、knowledge-graph 631 行），数据获取、ECharts 配置、UI 三层混在一个文件。
- **建议**：引入 SWR（轻、无侵入），把图表配置抽 `components/charts/*`；不必大重构，新增页面先用新模式即可。

### 🟢 低严重度

| # | 问题 | 位置 | 建议 |
|---|---|---|---|
| P3-1 | assistant 死代码 5 个文件占位（redirect/404 假体） | `src/app/assistant/*`、`api/assistant/*` | 环境支持时物理删除；当前占位可接受 |

## 三、技术选型评价

| 选型 | 评价 |
|---|---|
| Next.js 16 App Router + React 19 | ✅ 合理，三端同仓、API 与页面对称，适合本项目规模 |
| Drizzle ORM | ✅ 合理，类型安全好；但 relations 能力未用起来（P3-2） |
| sql.js 内存库 | ⚠️ 环境妥协下的选择，演示合格、生产不合格（P1-1） |
| jsonwebtoken（自管 JWT） | ✅ 基本合理；配合启动时随机密钥告警已闭环演示需求 |
| SHA-256 固定盐 | ❌ 需替换为慢哈希（P1-4） |
| 智谱 GLM-4-Flash + 分层批改 | ✅ 架构方向正确（规则引擎兜底 → AI 兜底），问题是 batch 路由未接入该管线（P1-2） |
| shadcn/ui + Tailwind 4 | ✅ 合理 |

## 四、总体结论

**作为高校答辩/演示项目：良好（约 7.5/10）。** 功能主线完整、三端体验统一、安全越权经两轮治理后已达演示级可信、代码风格一致、纯函数有测试——在这个体量（2.6 万行）的独立开发项目里属于完成度较高的水平。

**作为生产系统：尚不可交付（约 4/10）。** 核心短板按优先级为：内存库的持久化与原子性（P1-1）→ 业务逻辑无 service 层且双批改引擎并存（P1-2）→ 权限靠约定无强制（P1-3）→ 慢哈希缺失（P1-4）→ 集成测试为零（P2-3）。

**若继续演进，投入产出比最高的三步**：
1. 迁移 better-sqlite3/libsql（一劳永逸解决 P1-1，顺带获得真事务支撑 P2-1）；
2. 抽 grading service 统一批改管线，删除 batch 内置引擎（消除数据不一致）；
3. 补「权限矩阵」集成测试，把本轮安全修复永久锁住。

完成这三步后，项目即可从「高质量演示」跨入「可小规模试运行」档位。
