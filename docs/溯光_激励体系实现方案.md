# 溯光 TracingLight · 签到 / 积分 / 商店 实现方案

> 版本：v1.0（待确认）　|　日期：2026-09-05
> 范围：仅方案与建议，**不含代码实现**，确认后再进入开发
> 技术前提：Next.js 16 App Router + SQLite（sql.js 内存库 + 30s/即时双落盘）+ Drizzle ORM + JWT 鉴权 + 单进程（无 Redis）

## 0. 设计总览

### 0.1 定位与原则

激励体系服务于**学习行为**，而非单纯打卡。设计遵循三条原则：

1. **积分与真实学习绑定**：签到只是入口，主要积分来自作业得分、错题复习、答疑提问等有效学习行为，避免"签到即走"。
2. **零履约成本优先**：商店一期只上虚拟权益与特权皮肤，避开实物发货的物流与审核负担。
3. **可配置、可扩展**：获取/消耗系数、商品类型、积分有效期全部配置化，便于答辩演示时实时调整。

### 0.2 适用范围

| 角色 | 签到 | 积分 | 商店 |
|---|:---:|:---:|---|
| 学生 | ✅ 主使用者 | ✅ 获取与消耗 | ✅ 浏览与兑换 |
| 教师 | — | 手动加分（课堂表现）、查看班级积分榜 | 订单核销（虚拟权益） |
| 管理员 | — | 规则配置、异常对账、积分封禁 | 商品 CRUD、库存管理 |

### 0.3 与现有模块的衔接

激励体系不新建闭环，而是**挂在已有链路上做埋点**：

```
作业提交 → AI 批改 → 得分
                    └→ [埋点] 得分积分
错题归档 → 完成复习
                    └→ [埋点] 复习积分
AI 答疑 → 有效提问
                    └→ [埋点] 答疑积分
材料阅读 → 时长达标
                    └→ [埋点] 阅读积分（复用 behavior_log）
每日签到 ────────────────→ [埋点] 签到积分
                                    ↓
                              积分账户 → 流水
                                    ↓
                              商店兑换 → 订单
```

## 1. 业务目标与核心规则

### 1.1 每日签到

**业务目标**：建立每日打开平台的习惯，形成"日活锚点"。

**核心规则**：

| 项 | 规则 | 说明 |
|---|---|---|
| 签到周期 | **7 天循环**：第 1-6 天基础分递增，第 7 天大奖 | 周期短、反馈快；7 天大奖制造期待 |
| 基础奖励 | D1: 2 分 / D2: 3 / D3: 5 / D4: 5 / D5: 8 / D6: 8 / D7: 20 | 累计满周期 51 分 |
| 连续加成 | 连续 ≥ 7 天后，每日基础分 +2（封顶 +10） | 长线激励不断签 |
| 断签处理 | 连续天数归零，从 D1 重新计；**可用补签卡补救** | 降低挫败感 |
| 月度重置 | 每月 1 日重置"本月签到次数"，连续天数**跨月保留** | 避免月初断签感 |
| 补签机制 | 每张补签卡补 1 天（限**当月内**的漏签日期） | 关键留存手段 |
| 补签卡获取 | ① 连续满 7 天赠送 1 张（上限 3 张）② 商店 30 分兑换 | 双通道获取 |

**关键状态**：
- `未签到`（今日未签）
- `已签到`（今日已签，显示下一次奖励预览）
- `可补签`（存在当月漏签日且持有补签卡）

### 1.2 积分体系

> 🔄 **v1.1 修订（用户确认）**：积分拆分为**总积分**与**可用积分**两个口径，排行榜按**总积分**计算，商城消费扣**可用积分**。详见 §8。

**业务目标**：量化学习投入，为商店兑换与班级排行提供统一度量。

**双口径定义**：

| 口径 | 字段 | 特性 | 用途 |
|---|---|---|---|
| **总积分**（累计） | `total_earned` | **只增不减**，兑换、过期都不减少 | 排行榜、等级、成就、教师评价 |
| **可用积分**（余额） | `balance` | 可增可减 | 商城兑换、购买补签卡 |

换算关系：`balance = total_earned − total_spent − expired`

> 这样设计的好处：学生兑换商品后**排名不会掉**（避免"花钱掉榜"的负向体验），排行榜真实反映"累计学习投入"。

**获取途径**（一期）：

| 来源 | 积分 | 触发点 | 日上限 |
|---|---|---|---|
| 每日签到 | 2-20 | 签到接口 | 1 次/日 |
| 作业提交 | 5（提交即得） | submit 接口 | — |
| 作业得分 | `round(得分率 × 20)` | 批改完成 | 100 |
| 错题复习完成 | 3 | errors PATCH（reviewing） | 30 |
| 举一反三满分 | 10 | practice 提交 | 30 |
| AI 答疑有效提问 | 2 | assistant 接口 | 20 |
| 材料阅读满 10 分钟 | 5 | behavior_log 累计 | 15 |
| 教师手动奖励 | 教师自定（1-50） | 教师端加分 | — |

**消耗途径**：
- 商店兑换（主要出口）
- 补签卡购买（30 分/张）

**有效期**（建议二期）：积分按**获得年度**过期（如 2026 年度积分于 2027-03-31 清零），过期前 30 天与 7 天各推送一次提醒。一期可先不做过期，但**流水表需预留过期字段**。

### 1.3 积分商店

**业务目标**：给积分一个出口，让激励闭环，同时反哺学习。

**商品类型**（一期只上前两类）：

| 类型 | 示例 | 履约方式 | 库存 | 一期 |
|---|---|---|---|---|
| **虚拟装饰** | 头像框、个人主页皮肤、称号 | 即时生效（写 user 扩展字段） | 无限 | ✅ |
| **学习权益** | PDF 学情报告导出次数、错题 AI 深度解析加速券 | 即时生效（写权益计数） | 限量 | ✅ |
| **实物周边** | 笔记本、文具、学院周边 | 教师线下发放 + 订单核销 | 限量 | ⬜ 二期 |
| **特权类** | 免作业退回一次、延期提交券 | 影响评分公平性，**不建议上线** | — | ❌ |

> ⚠️ **明确不上线特权类商品**：如"免退回券""加分券"会破坏成绩公平性，在高校答辩场景中是扣分项。

**兑换流程**：

```
浏览商品 → 点击兑换（二次确认弹层）
        → 校验（登录/商品在售/库存/积分/每人限购/活动有效期）
        → 事务：扣积分 + 扣库存 + 生成订单
        → 虚拟商品：订单自动 completed，权益即时到账
        → 实物商品：订单 paid → 教师端核销 shipped → completed
        → 取消/退款：回滚积分与库存
```

**限购规则**：`per_user_limit` 字段控制（默认 0=不限），按 `user_id + item_id` 统计已完成订单数。

## 2. 模块关系、数据流转与表设计

### 2.1 数据流转链路

```
[用户行为]
   │
   ├─ 签到/学习/作业 ──► 积分服务 awardPoints()
   │                          │
   │                          ├─ 1. 校验幂等键（防重复发放）
   │                          ├─ 2. 校验日上限
   │                          ├─ 3. 事务：更新账户余额 + 写流水
   │                          └─ 4. 发通知（可选）
   │
   ▼
[points_account] ◄── 余额快照 ──► [points_ledger]（每笔流水）
   │
   ▼
[兑换] redeem()
   │
   ├─ 1. 校验商品状态/库存/限购/积分充足
   ├─ 2. 条件更新库存：UPDATE stock WHERE id=? AND stock>0（防超卖）
   ├─ 3. 条件扣减积分：UPDATE balance WHERE user_id=? AND balance>=cost
   ├─ 4. 写订单 + 写流水（积分消耗）
   └─ 5. 虚拟品即时 completed；实物品 pending 待核销
```

### 2.2 数据表设计（Drizzle 风格，字段与现有 schema 命名一致）

#### ① `points_account` 积分账户（每学生一行）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | integer PK | |
| user_id | integer FK→user.id **UNIQUE** | 一个学生一个账户 |
| **total_earned** | integer default 0 | **总积分（累计获得，只增不减）— 排行榜依据** |
| **balance** | integer default 0 | **可用积分（商城可消费）** |
| total_spent | integer default 0 | 累计消耗（对账用） |

| level | integer default 1 | 积分等级（二期：铜/银/金） |
| **rank_visible** | boolean default true | **是否参与排行榜（隐私开关）** |
| updated_at | text | |

### 3.4 关键状态定义

**签到状态**（GET /checkin 返回）：

| 状态 | 含义 | 前端表现 |
|---|---|---|
| `not_signed` | 今日未签 | 主按钮"立即签到" |
| `signed` | 今日已签 | 显示明日奖励预览 |
| `can_remedy` | 存在可补签日且持卡 | 日历上漏签日高亮 |

**订单状态机**：

```
                ┌──────────┐
                │ pending  │  下单成功（实物待审核）
                └────┬─────┘
        ┌────────────┼────────────┐
        ▼            ▼            ▼
   ┌────────┐  ┌──────────┐  ┌────────────┐
   │ paid   │→ │ shipped  │→ │ completed  │
   └───┬────┘  └──────────┘  └────────────┘
       │
       ▼
  ┌──────────┐   ┌────────────┐
  │cancelled │   │  refunded  │  回滚积分+库存
  └──────────┘   └────────────┘
```

- 虚拟商品：下单即 `completed`（跳过 paid/shipped）
- 实物商品：`pending` →（教师审核）→ `paid` → `shipped` → `completed`

**异常状态与错误码**：

| 场景 | HTTP | code | 文案 |
|---|---|---|---|
| 重复签到 | 409 | `ALREADY_SIGNED` | 今天已经签到过啦 |
| 补签卡不足 | 400 | `NO_REMEDY_CARD` | 补签卡不足，可在商店兑换 |
| 补签跨月 | 400 | `REMEDY_OUT_OF_MONTH` | 只能补签本月内的漏签日期 |
| 积分不足 | 400 | `INSUFFICIENT_POINTS` | 积分不足，还差 X 分 |
| 库存不足 | 409 | `OUT_OF_STOCK` | 该商品已被抢完 |
| 超出限购 | 400 | `LIMIT_EXCEEDED` | 每人限购 X 件 |
| 商品下架 | 404 | `ITEM_OFF_SHELF` | 商品已下架 |
| 积分日上限 | 200 | `DAILY_CAP_REACHED` | 今日该类积分已达上限（**不算错误，正常返回但积分为 0**） |
| 功能未开启 | 403 | `FEATURE_DISABLED` | 激励功能未开启 |
| 越权操作他人 | 403 | `FORBIDDEN` | 无权操作 |

## 4. 边界情况与风险控制

### 4.1 防刷策略

| 风险 | 处理 |
|---|---|
| 重复签到 | `UNIQUE(user_id, sign_date)` 数据库约束 + 幂等键，**双保险** |
| 客户端改时间 | **一律使用服务端时间**（`new Date()` 在服务端），不信任任何客户端日期参数（补签的 date 参数需校验在当月且 < 今天） |
| 刷作业积分 | 同一 `grading_task_id` 只能产生一次积分（`biz_ref` 唯一性校验） |
| 刷答疑积分 | 按用户+自然日频率限制（内存令牌桶，参考现有登录限流实现） |
| 刷阅读时长 | 单次上报时长上限（如 ≤30 分钟）、日累计上限（如 ≤4 小时），超出不计分 |
| 异常暴涨 | 日获取总量硬上限（如 200 分/日），超限仍返回成功但积分为 0 并记审计日志 |

### 4.2 并发扣减（库存与积分）

当前是**单进程 sql.js 内存库**，Node 事件循环使写操作天然串行，但**仍需正确的 SQL 保证正确性**（未来迁移 better-sqlite3/Postgres 时必须成立）：

```sql
-- 库存扣减：条件更新 + 检查影响行数（防超卖）
UPDATE shop_item SET stock = stock - 1, version = version + 1
WHERE id = ? AND stock > 0 AND version = ?;
-- affectedRows === 0 → 库存不足，直接返回 OUT_OF_STOCK

-- 积分扣减：条件更新（防透支）
UPDATE points_account SET balance = balance - ?, total_spent = total_spent + ?, version = version + 1
WHERE user_id = ? AND balance >= ? AND version = ?;
-- affectedRows === 0 → 余额不足或并发冲突，重试或返回错误
```

**事务边界**（一个事务内完成）：
1. 库存条件扣减
2. 积分条件扣减
3. 插入订单
4. 插入积分流水
5. 虚拟商品：写权益到账

任一步失败 → **整体 rollback**（sql.js 用 `db.transaction()` 或手动 begin/commit/rollback）。

**下单幂等**：客户端生成 `idempotency_key`（UUID），服务端 UNIQUE 约束；重复提交直接返回首次订单。

### 4.3 积分对账

**对账公式**：`balance == SUM(earn) - SUM(spend) - SUM(expire) ± SUM(adjust)`

**三层保障**：

1. **写入时**：每笔流水记录 `balance_after`，形成链式快照
2. **每日校验**：学生首次访问积分页时，比对账户余额与流水汇总（轻量，单次聚合查询）；不一致则写 `audit_log` 并自动以流水重算修正
3. **管理端手动**：`/api/admin/points/reconcile` 全量对账，输出差异报告（答辩时可演示）

**不允许**：直接 UPDATE 余额而不写流水（代码评审红线）。所有变更必须走 `awardPoints()` / `spendPoints()` 统一入口。

### 4.4 其他风险

| 风险 | 应对 |
|---|---|
| 数据丢失（sql.js 30s 落盘） | 积分/订单属关键写路径，必须调用 `saveDb()` 即时落盘（与现有批改/退回一致的做法） |
| 学生删号/转班 | 积分跟随 user_id，转班不影响；**不做积分转移**（一期） |
| 商品下架后已有订单 | 订单保留 `points_cost` 与商品快照字段，下架不影响历史订单展示 |
| 积分通胀 | 管理端可配置系数；观察 2 周后调参 |
| 教师乱加分 | 单次上限 50 分、需填理由、写 `operator_id` + 审计日志 |

### 6.4 需要避免的坑（来自同类产品经验）

1. **不要做"加分券/免退回券"**——破坏成绩公平性，答辩时是明显扣分项
2. **不要一上来做实物商城**——物流、审核、核销成本高，先用虚拟品跑通闭环

## 8. 修订：总积分 / 可用积分分离 + 排行榜设计（v1.1）

> 依据用户 2026-09-05 补充需求：学生总积分与商城积分隔开，并按积分排名。

### 8.1 双口径模型

```
                    ┌─────────────────────────┐
   学习行为 ──────► │  total_earned（总积分）  │  只增不减
   签到/作业/复习   │  排行榜 · 等级 · 成就    │
                    └───────────┬─────────────┘
                                │ 同步累加
                                ▼
                    ┌─────────────────────────┐
                    │   balance（可用积分）    │  可增可减
                    └───────────┬─────────────┘
                                │ 兑换扣减
                                ▼
                    ┌─────────────────────────┐
                    │  total_spent（已消耗）   │
                    └─────────────────────────┘
```

**不变式**：`balance = total_earned − total_spent − expired`

**设计收益**：学生兑换商品后**排名不掉**——避免"花积分 = 掉榜"的负向反馈，排行榜真实反映累计学习投入，同时保留商城消费动力。

### 8.2 前端展示规范

| 位置 | 展示内容 |
|---|---|
| 学生首页积分卡 | **总积分**（大字，带排名"班级第 X 名"）+ 可用积分（小字，带"可消费"标签） |
| 积分详情页 | 双卡并列：总积分（含累计获得/排名/等级）、可用积分（含消费入口） |
| 商城顶部条 | 只显示**可用积分**：`可用 320 分`（避免与总积分混淆） |
| 兑换确认弹层 | "消耗 80 可用积分，剩余 240 分 · **总积分与排名不受影响**"（明确消除顾虑） |
| 流水列表 | 每条标注影响口径：获得显示 `总积分 +5 / 可用 +5`；消费显示 `可用 −80` |

### 8.3 排行榜设计

#### 榜单维度

| 榜单 | 口径 | 范围 | 更新频率 |
|---|---|---|---|
| **班级总榜** | total_earned | 同 class_id | 实时 |
| **班级周榜** | 本周流水 SUM(amount where direction=earn) | 同 class_id | 实时 |
| **全校总榜**（二期） | total_earned | 全体学生 | 实时 |
| **好友榜**（三期） | total_earned | 互相关注 | 实时 |

> 一期实现：**班级总榜 + 班级周榜**两个 Tab。

#### 排序规则

```sql
-- 总榜
SELECT u.id, u.real_name, u.avatar, a.total_earned
FROM points_account a JOIN user u ON u.id = a.user_id
WHERE u.class_id = ? AND a.rank_visible = 1 AND u.role = 'student'
ORDER BY a.total_earned DESC, a.updated_at ASC   -- 同分先达成者靠前
LIMIT 50;

-- 周榜（按时间窗口聚合流水）
SELECT l.user_id, SUM(l.amount) AS week_points
FROM points_ledger l JOIN user u ON u.id = l.user_id
WHERE l.direction = 'earn' AND l.created_at >= ? AND u.class_id = ?
GROUP BY l.user_id
ORDER BY week_points DESC
LIMIT 50;
```

- 周榜起始时间：**本周一 00:00**（服务端时间），与签到周期解耦
- 索引需求：`points_ledger(user_id, created_at)`、`points_account(total_earned)`

#### 返回结构（含"我"的位置）

```jsonc
{
  "success": true,
  "data": {
    "scope": "class",
    "period": "total",
    "list": [
      { "rank": 1, "user_id": 5, "name": "张同学", "points": 486 },
      { "rank": 2, "user_id": 9, "name": "李同学", "points": 431 }
    ],
    "me": {
      "rank": 12,
      "points": 268,
      "gap_to_prev": 23,       // 距上一名还差多少分
      "percentile": 0.68       // 超过了 68% 的同学
    },
    "updated_at": "2026-09-05 12:00:00"
  }
}
```

> 长尾优化：榜单只返回前 50 名 + **始终附带"我"的条目**（若我在 50 名外，`list` 末尾追加我与前后各 2 名，形成"附近排名"切片）。

#### 接口

| 方法 | 路径 | 参数 | 说明 |
|---|---|---|---|
| GET | `/api/student/points/ranking` | `scope=class`、`period=total\|week` | 排行榜 + 我的位置 |
| PUT | `/api/student/points/rank-visibility` | `{ visible: boolean }` | 隐私开关（不上榜） |

**异常与边界**：

| 场景 | 处理 |
|---|---|
| 班级无人有积分 | 返回空 list + 空态文案"还没有同学获得积分，快来抢第一" |
| 我已关闭上榜 | `me` 返回 `{ rank: null, hidden: true }`，提示"你已关闭上榜" |
| 周榜当周无数据 | 降级展示提示，Tab 上标注"本周暂无" |
| 越权查其他班 | `scope` 仅取当前学生所属班级，不接受客户端传 class_id |

| 章节 | 修订点 |
|---|---|
| §1.2 积分体系 | 新增双口径定义与换算关系 |

### 8.5 防刷与风险（排行榜专项）

| 风险 | 应对 |
|---|---|
| 刷榜（刷作业/答疑冲分） | 已由日上限（200/日）与单业务 ID 唯一发分控制；周榜同样受限 |

| 负向体验（垫底挫败） | `me` 只返回 percentile（超过 X% 同学）而非"倒数第几"；周榜重置给每个人新机会 |

### 9.3 装备系统（新增表）

装饰类商品需要"背包 + 装备"机制，新增 **第 7 张表**：

#### ⑦ `user_decoration` 背包与装备

| 字段 | 类型 | 说明 |
|---|---|---|
| id | integer PK | |
| user_id | integer | |
| item_id | integer FK→shop_item.id | 来源商品 |
| subtype | text | `avatar_frame`/`chat_bubble`/`name_color`/`font`/`profile_theme`/`title`/`effect` |
| config_key | text | 具体样式键（如 `frame_starlight`、`color_gold`） |
| config_value | text NULL | 样式值（如色值/字体栈，便于扩展自定义） |
| source | text | `purchase` / `achievement` / `grant` |
| is_equipped | boolean default false | **同 subtype 只能装备 1 个** |
| acquired_at | text | |
| expire_at | text NULL | 预留：限时装饰 |

**索引**：`UNIQUE(user_id, item_id)`（防重复购买同款）、`idx(user_id, subtype, is_equipped)`

**装备逻辑**：
```
兑换装饰 → 写 user_decoration（is_equipped=false）
       → 自动装备该 subtype（同 subtype 其他项全部置 false）
点击"装扮"页 → 切换装备（UPDATE 同 subtype 全部 false → 目标 true）
```

**生效位置**：

| 装饰 | 生效处 | 前端改造点 |
|---|---|---|
| 头像框 | 侧栏用户区、排行榜、评论区、学生列表 | 头像组件加 `frame` prop |
| 昵称颜色 | 同上所有昵称处 | 昵称组件读装备色值 |
| 称号 | 昵称后 badge | 同上 |
| 字体 | 全局（写 localStorage + 启动时注入 CSS 变量） | 根布局注入 `--app-font` |
| 主页皮肤 | 学生个人主页 | 主页容器加 theme class |
| 气泡 | AI 答疑会话 | 消息组件读装备样式 |
| 入场特效 | 登录/签到成功时 | 触发点播放一次 |

**性能与实现**：装备信息在**登录时随用户信息一起返回**（`/api/auth/login` 扩展 `equipments` 字段），避免每次渲染查询；切换装备即时生效并写库。

### 9.4 商品管理（管理端）

管理端 `/api/admin/shop/items` 支持：
- 上下架、改价、改库存（**不改已购用户的装备**）
- 新增商品只需填 `type/subtype/config_key/price`，前端按 subtype 自动渲染对应样式（枚举化扩展）
- 限时商品：`start_at/end_at`，到期自动下架并提示

### 9.7 风险与注意

| 风险 | 应对 |
|---|---|
| 装饰过多导致视觉噪音 | 稀有度分级 + 默认只展示已装备；限定款制造稀缺 |
| 字体修改影响可读性 | 只提供 4 款经过验证的字体栈，不做自由字号/行距修改 |
| 全局字体切换闪烁 | 服务端随登录返回 + localStorage 首屏注入，避免 FOUT |
| 重复购买同款 | `UNIQUE(user_id, item_id)` + 前端已购显示"已拥有" |
| 高价值商品被误兑 | 二次确认弹层（≥200 分额外确认） |
