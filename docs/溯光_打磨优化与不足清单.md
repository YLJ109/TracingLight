# 溯光 TracingLight · 打磨优化与不足点清单

> 版本：v1.0　|　日期：2026-09-04　|　背景：完成全功能测试与安全修复后的二次打磨
> 结论：核心流程端到端可运行、无报错；本轮新增修复「运行时写操作不落盘」这一隐蔽 P0 缺陷。

## 一、本轮端到端验证结果

### 1.1 API 可用性（实测 HTTP 状态）

| 端 | 接口 | 结果 |
|---|---|---|
| 学生端 | profile / errors / assignments / knowledge-graph / study-plan / recommend / schedule / materials / triple-graph | 全部 200 ✅ |
| 教师端 | courses / students / assignments / analytics / exams / announcements / questions/bank | 全部 200 ✅ |
| 管理端 | overview / users / logs / config | overview/logs/config 200；users 405（见不足点 #5） |

### 1.2 安全修复回归验证

| 验证项 | 结果 |
|---|---|
| 未登录访问 triple-graph / errors / teacher-courses | 全部 401 ✅ |
| 学生越权查他人学情（student_id=4） | 仍返回本人「张同学」✅ |
| 学生不带参查错题 | 211 → 19 条（仅本人）✅ |
| 提交不属于作业的题目（question_id=999） | 返回「提交了不属于该作业的题目」✅ |
| 提交他人身份（student_id=4） | 后端强制以本人 userId=3 处理 ✅ |

### 1.3 本轮新发现并修复的缺陷

**P0：运行时写操作不落盘。** `saveDb()` 只在 seed 和进程退出时调用，运行期的提交/批改/改错题只写内存。已修复：`db.ts` 增加「每 30 秒定时静默持久化 + 进程退出保存」双保险，强杀/崩溃最多丢 30 秒数据。

## 二、不足点清单（按优先级排序）

### 🔴 P0 — 影响稳定性/正确性（建议立即处理）

| # | 问题描述 | 影响范围 | 改进方向 | 预期收益 |
|---|---|---|---|---|
| 1 | **数据库仍为 sql.js 内存库**：整库载入内存、全量序列化导出（944KB），并发写不安全 | 全站数据读写；多人/高频写场景卡顿；极端情况内存溢出 | 迁移 better-sqlite3（WAL + 写队列 + busy_timeout），Drizzle 仅换 driver | 写入性能提升 10×+，崩溃不丢数据，支持并发写，消除最大技术债 |

### 🟠 P1 — 高（影响质量与可维护性）

| # | 问题描述 | 影响范围 | 改进方向 | 预期收益 |
|---|---|---|---|---|
| 2 | **零自动化测试**：无任何 `.test/.spec` 文件，本轮安全修复也靠手工 curl 验证 | 每次改动都有回归风险，越权类 bug 易复发 | 补 Vitest 单测（规则引擎/鉴权工具/越权用例）+ agent-browser E2E 主链路 | 回归拦截，缺陷早发现，重构有安全网 |
| 3 | **AI 接口错误信息透传**：`ai/grade`、`ai/assistant`、`ai/report` 等 catch 直接返回 `error.message` | AI 相关接口；可能泄露 API 内部细节/密钥错误信息 | 统一脱敏为「AI 服务暂时不可用」，详情只写服务端日志 | 降低信息泄露面，提升错误友好度 |
| 4 | **学情数据仍混用 mock**：`profile` 的 radarData/trendData/errorData/courseComparison 仍是 `generateStudentData` 生成 | 学生端学情看板；与教师端真实口径不一致，答辩可能被追问 | 将雷达/趋势/课程对比全部切换为真实 gradingTask/masteryLog 聚合 | 数据口径一致，学情可信，答辩经得起追问 |

### 🟡 P2 — 中（影响规范性与完整性）

| # | 问题描述 | 影响范围 | 改进方向 | 预期收益 |
|---|---|---|---|---|
| 5 | **admin/users 无 GET**：用户列表由 `overview` 顺带返回，`GET /api/admin/users` 返回 405 | 管理端用户管理；RESTful 语义不完整 | 补 `GET /api/admin/users` 返回用户列表，页面改为直接调用 | API 语义规范，前后端职责清晰 |
| 6 | **前端冗余传 student_id**：后端已改为 `userId` 归属，但前端 8 个页面仍传 `student_id` 参数（被静默忽略） | 学生端页面；契约冗余，易误导后续维护者 | 前端清理无用 `student_id` 传参，统一从 token 取用户 | 代码更清晰，减少「为何传了不生效」的困惑 |
| 7 | **JWT_SECRET 使用示例默认值**（`.env.example` 为 `change_this...`） | 认证体系；若未替换则 Token 可被伪造 | 部署时生成强随机密钥；启动时检测默认值并告警 | 消除认证被伪造风险 |
| 8 | **无 service 层**：业务逻辑散落在 35+ 个 route，方案宣称的「六层架构」实际是「API 直查库」 | 全部业务逻辑；可维护性、可测试性差 | 抽 service/domain 层，route 只做参数解析与响应 | 逻辑可复用、可单测，符合方案架构 |
| 9 | **登录限流为进程内存级**：重启失效、多实例不共享 | 登录接口；本地单机够用，生产不满足 | 生产换 Redis 限流；本地保留内存版 | 生产环境防暴力破解可靠 |
| 10 | **notifications 接口无角色限定**（`requireAuth` 未传 role） | 通知接口；当前按 userId 过滤无实际越权 | 补 `requiredRole` 或明确注释，统一鉴权规范 | 鉴权一致性，避免未来改动引入越权 |

### 🟢 P3 — 低（体验与细节）

| # | 问题描述 | 影响范围 | 改进方向 | 预期收益 |
|---|---|---|---|---|
| 11 | **loading/空状态/错误提示风格不统一**：各页面骨架屏、空态文案、错误提示措辞不一致 | 全站 UX | 统一 Loading 组件、空态组件、错误 Toast 规范 | 体验一致，观感更专业 |
| 12 | **triple-graph 无缓存**：knowledge-graph 有缓存，triple-graph 每次全量查库 + 内存 filter | 三图谱页面 | 复用缓存机制 + SQL join 替代内存 filter | 响应更快，减少无谓计算 |
| 13 | **方案文档二级标题编号错位**（八章用 7.x、九章用 8.x） | 文档一致性 | 全文档编号校正 | 文档专业、可追溯 |
