## 一、审查结论（一句话）

**核心功能基本落地（约 75%），门面与主线闭环可用，但存在三处「看得见、一用就露馅」的缺口：助教端是只读空壳、管理后台多为静态占位、主观题复核闭环只有"改分"没有"留痕与申诉"。** 方案层面骨架是 A 级，执行层面仍欠最后一公里。

## 三、多角度改进建议

### 3.1 架构合理性（最重要）

| 问题 | 影响 | 建议 |
|---|---|---|
| **sql.js 内存库 + 手动 `saveDb`** | 进程崩溃/断电即丢数据，每次全量导出（880KB） | 这是唯一"必须返工"的点。至少加「定时自动保存（如每 30s）+ 退出兜底」；长期换 better-sqlite3（一行驱动切换，Drizzle 不变） |
| **无 Service 层** | 业务逻辑散落在 35 个 route 里，六层架构形同虚设 | 抽 `src/lib/services/`（grading/analytics/material），route 只做鉴权+入参校验 |
| **schema 双份维护** | `getCreateTableSQL` 原始 SQL + Drizzle 对象易不同步 | 引入 `drizzle-kit generate` 生成迁移，单一来源 |

### 3.2 代码质量

- **大量 `any`**：`analytics/page.tsx`、多个 route 里 `data: any`，失去类型保护；
- **硬编码**：`teacher_id: 1`、`class_id: 1` 散落，换演示账号会错乱；
- **零测试**：无 `.test/.spec` 文件，方案 P0 要求"核心模块单测 ≥70%"未达成。

### 3.3 性能

- sql.js 全量内存 + 全量导出，数据增长后 saveDb 会成为瓶颈；
- ECharts 在多页面重复 `init`/`dispose`，无实例复用、无按需懒加载；
- AI 调用无缓存（方案明确要求"缓存复用"），相同题重复批改重复计费。

### 3.4 安全

| 问题 | 严重度 | 建议 |
|---|---|---|
| **登录无密码校验** | 🔴 高 | `user` 加 `password` 字段 + bcrypt 校验（演示可保留便捷登录开关，但答辩需讲清"密码已哈希存储"） |
| JWT 无刷新/吊销 | 🟡 中 | 加 `iat` 校验 + 登出黑名单（本地演示可简化） |
| 越权校验不完整 | 🟡 中 | 逐一核对：学生只能查自己数据、教师只能查自己课程、助教只能查被分配提交 |
| AI Key 硬编码/环境变量 | 🟡 中 | 确认 `.env` 不入库、Key 不泄漏 |

### 3.5 可维护性

- 无 Drizzle 迁移工具，改表靠"删库重 seed"——演示数据会丢；
- **主题残留**：`announcements`、`exams`、`students` 等页面仍是 teal 旧色，与粉紫主色不一致（之前 grep 确认 `teal-600` 仍散落）；
- 移动端底部 `pb-20` 与部分页面 `h-full` 存在潜在冲突。

### 3.6 用户体验

- 移动端窄屏需逐页验证（方案强调移动端优先）；
- 助教端/管理后台的"空壳感"会让答辩评委一眼看穿；
- 空状态/加载态部分页面缺失，异常反馈不统一。

## 四、补充方案（按优先级，可直接执行）

### 🔴 P0 答辩前必做（否则露馅）

1. **登录加密码校验**：`user` 表加 `password`（bcrypt 哈希），登录 API 校验；保留"演示账号自动填入"，但后端真实校验。工作量小、收益极大。
2. **助教端补批改操作**：任务池 → 认领 → 逐题批改（复用现有 `grade` 页批改逻辑）→ 提交复核 → 教师终审。补上 `review_record` 留痕。
3. **管理后台补真实功能**：用户管理（新增/禁用/重置密码/改角色）+ `audit_log`/`system_config` 表 + 日志审计/系统设置落地。

### 🟡 P1 答辩前建议

4. **通知闭环**：`notification` 表 + 教师发布作业时生成通知 + 学生端 `NotificationBell` 展示 + 未读红点。
5. **主观题分级复核**：置信度 ≥0.85 批量通过（抽查开关）、<0.6 强制人工，补"驳回重判"与"学生申诉"。
6. **AI 答疑持久化**：`qa_session`/`qa_message` 表，答疑历史可回溯。

### 🟢 P2 加分项

7. **推荐路径图**：复用图谱 DAG 可视化，实现"薄弱→前置补漏→巩固→目标"路径。
8. **补测试**：`src/lib` 与核心 API 单测，`agent-browser` 走登录→作答→批改主链路 E2E。
9. **better-sqlite3 迁移**（答辩作为"技术亮点"口头讲即可，代码不强制）。

## 五、总结

| 维度 | 评分 | 说明 |
|---|---|---|
| 功能完整度 | 75% | 主线闭环可用，助教/后台/主观题闭环欠最后一公里 |
| 架构合理性 | B | 六层架构未真正落地，sql.js 是最大技术债 |
| 代码质量 | B- | 无测试、any 泛滥、硬编码 |
| 安全 | B- | 登录无密码校验是硬伤 |
| 可维护性 | B | 双份 schema、无迁移、主题残留 |
| 用户体验 | B+ | 粉紫主题统一、门面好，但空壳页拉低整体 |

**一句话建议**：不要再加新功能，集中把「密码校验、助教批改、管理后台真实性、主观题复核闭环」这四块补实，就能从"能演示"升到"经得起追问"。
