## 二、异常问题清单（按严重程度排序）

### 🔴 T-1（测试期间新发现，最高优先级）批量批改主链路绕过修复管线，数学等价批改在实际使用路径上未生效

- **错误表现**：同一份填空题答案，单题批改引擎（`objective-grading.ts`）与批量批改内置引擎得分严重分歧——「4分之1」「四分之一」「25%」「0.250」对参考答案「0.25」，前者满分 10 分，**后者 0 分**（4/5 用例不一致）。
- **触发条件**：教师端任意批量批改操作——实测确认前端 **3 处主链路全部调用 `/api/ai/grade/batch`**（`teacher/assignments/page.tsx:213`、`teacher/assignments/[id]/grade/page.tsx:120`、`teacher/assignments/[id]/page.tsx:92`），而当初修复的数学等价/多选半对/AI 四维评分只接入了 `ai/grade` 单题管线（前端无直接调用）。
- **可能原因**：当初「4分之1 判 0 分」的修复只替换了 `ai/grade` 的批改路径，`grade/batch` 路由内留存一套独立的简化引擎（精确匹配 + 包含即半分 + 主观题长度比/词重合启发式），从未同步。**这正是"无 service 层、逻辑多处复制"（P1-2）造成缺陷修复不彻底的实证案例。**
- **影响**：① 教师实际批改结果与单测验证的能力不符，"4分之1=0分"缺陷在批量路径**至今仍在复现**；② 主观题"AI 批改"在批量路径根本未调用 AI，四维分是按比例凑出的假数据；③ 错题归档/掌握度统计基于错误分数。
- **建议**：`grade/batch` 内部改为循环调用统一批改管线（objective-grading → AI 兜底），删除内置简化引擎——这是 P1-2 建议的最小落地版本，预计改动集中在 1 个路由文件。

### 🔴 T-2 崩溃数据丢失窗口 30 秒（P1-1 实证）

- **错误表现**：D1 用例——错题状态写入 `mastered` 后 25 秒内强杀进程，重启后状态回退为 `reviewing`，**写入丢失**。
- **触发条件**：任意写操作后 30 秒内进程被杀/断电/崩溃。
- **D2 对照 ✅**：写入后等待 36 秒（跨过落盘周期）再强杀，重启后数据完整保留——**定时落盘兜底机制本身有效**。
- **可能原因**：sql.js 纯内存运行，30 秒 `setInterval` 全量快照是唯一持久化路径（评审 P1-1 的精确边界确认）。
- **影响**：演示中若崩溃/强关终端，最近 30 秒内的提交、批改、标记全部蒸发且无任何提示。
- **建议**：短期可接受（兜底已验证有效）；根治仍以迁移 better-sqlite3/libsql 为准；低成本增强可在关键写路径（提交/批改完成后）追加一次即时 `saveToDisk`，把窗口缩到接近零。

### 🟡 T-3 输入校验断裂：类型错误返回 500 而非 400（P2-2 实证）

- **错误表现**：2 项异常——
  1. `POST /api/teacher/exams` 传 `course_id:"abc"`（非数字）→ **500**（内部错误，应为 400 参数错误）；
  2. 同接口 `exam_date` 传对象 `{"a":1}` → **500**。
- **触发条件**：前端异常状态/恶意构造/接口调试时传入错误类型。
- **可能原因**：`Number("abc")=NaN` 直接进 Drizzle 查询抛异常；无 zod/类型守卫，catch 兜底统一转 500（P2-2 所述"边界校验断裂"的直接后果）。
- **影响**：错误码语义失真（客户端无法区分自身参数错误与服务端故障）、日志噪音、潜在的异常信息面。
- **建议**：写接口引入 zod schema 校验（`safeParse` 失败返回 400 + 字段信息），优先覆盖 exams/assignments/submit 三个高频写接口。

### 🟡 T-4 推荐接口随机漂移（P2-5 实证）

- **错误表现**：同一学生连续两次调用 `GET /api/student/recommend`，`questionCount` 28→21、`lastPracticeDate` 日期漂移——**每次刷新数据都变**。
- **触发条件**：每次访问学生端推荐页。
- **可能原因**：`lib/mock-data-generator.ts` 内部随机数生成，`recommend` 路由未替换为库内真实聚合（P2-5 所列 3 个残留接口之一；`study-plan` 与 `ai/profile` 的 suggestions 实测确定性正常）。
- **影响**：演示时同一页面两次进入数据不一致，易被质疑数据真实性。
- **建议**：`recommend` 路由的 mock 字段替换为 knowledgeMasteryLog/errorBook 真实聚合（profile 已有现成聚合模式可复制），随后删除 mock-data-generator.ts。

### 🟡 T-5 密码慢哈希缺失（P1-4 定量实证）

- **实测数据**：10 万次 SHA-256（固定盐）仅 **191ms**——单机每秒可穷举约 52 万个口令；bcrypt 同等安全强度设计上需慢 4~5 个数量级。
- **触发条件**：`data/tracinglight.db` 文件一旦泄露（备份拷贝/仓库误提交）。
- **建议**：换 `bcryptjs`（纯 JS 无原生依赖），登录校验时对旧哈希透明重哈希平滑迁移。

### 🟡 T-6 批改流程无事务（P2-1 确认）

- **静态确认**：全项目仅 2 处 `.transaction()`；批改 = gradingTask + errorBook + knowledgeMasteryLog 三表写入，中途失败将产生"有成绩无错题/掌握度未更新"的不一致。
- **建议**：随 T-1 的管线统一一并包进事务（内存库事务零成本）。

### 🟢 T-7 低严重度静态项（确认属实，维持原建议）

| 项 | 实测结果 |
|---|---|
| assistant 死代码 | 5 个占位文件仍在（redirect/404 假体） |

| admin 首页原生 fetch | `admin/page.tsx:36` 用 `fetch` 未走统一 `apiFetch` |
| 依赖偏重 | 60 个运行时依赖 |
| 测试覆盖 | 现有 24 断言回归全绿，但 40 路由仍零集成测试（P2-3） |

## 四、结论

1. **前轮全部安全修复经运行时复测零回退**，权限矩阵与核心冒烟全绿；
2. **新发现 1 项高严重度功能缺陷（T-1）**：批量批改主链路未接入修复后的批改管线，"4分之1=0分"在教师实际使用的路径上仍会复现，且主观题 AI 批改在批量路径未生效——**建议作为下一个修复的最高优先级**（改动集中、收益直接）；
3. T-2/T-3/T-4/T-5 与架构评审判断完全吻合，均有实测数据支撑，可按报告建议排期处理；
4. 测试副产物 `tests/engine-consistency-check.ts`（双引擎对比脚本）已留存在 tests/ 目录，可后续纳入回归。

> 修复优先级建议：**T-1（批改管线统一）→ T-3（zod 校验）→ T-4（recommend 真实化）→ T-5（bcryptjs）→ T-6（事务）**；T-2 维持现状 + 关键写路径即时落盘增强。

## F-0 修复期间新发现并修复的潜伏缺陷

- **无意义答案判定误伤合法短答案**：原逻辑 `trimmed.length <= 3` 即判 0 分——「ABD」（多选）、「25%」、「1/4」等合法客观题答案都会被直接判 0 并跳过规则引擎（原 `ai/grade` 即存在，本次复制进 service 时暴露）。
- **修复**：客观题不做长度判定（交规则引擎），长度阈值仅用于主观题跳过 AI。
- **复验**：`computeGrade("ABD" vs "ABD")=10/10`；单测回归 26 断言全绿。
