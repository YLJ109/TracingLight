# 溯光智慧学习平台 · 全面整改企业级方案（V3 · Final）

> 状态：方案评审稿（尚未实施）   ·   适用范围：学生端 / 教师端 / 管理端
> 编写原则：先立「数据单一事实源」与「统一口径」，再改逻辑，最后重建种子并对账验收。
> 所有结论均带 `文件:行号` 证据，可复核、可验收。
> 覆盖范围：本次**全量功能审计 + 全量回归测试**下的全部已暴露缺陷（R1–R8），并给出企业级工程治理规范。

---

## 1. 摘要（Executive Summary）

本方案针对当前系统暴露的 **8 类核心缺陷** 设计系统性整改路径，而非逐点打补丁：

| # | 缺陷 | 用户感知 | 严重度 |
|---|------|---------|--------|
| R1 | 课程作用域无单一事实源 | 「我的学情」4门课 vs「作业」2门课 | **P0** |
| R2 | 掌握度/薄弱/统计口径破碎 | 总体「4薄弱」与底部「86薄弱」互相矛盾 | **P0** |
| R3 | 知识图谱筛选只改画布不改统计 | 「只有中间的能变，别的值不变」 | P1 |
| R4 | 错题本 ↔ 图谱 ↔ 掌握度无双向联动 | 两功能各自孤立，定位全靠人肉记忆 | P1 |
| R5 | 种子数据陈旧且关联不自洽 | 课程/知识点/错题归属错乱 | **P0** |
| R6 | 登录抽屉演示账号列表不可滚动 | 20 名学生账号挤在固定抽屉里无法下滑查看 | P1 |
| R7 | 演示账号口径冒烟未固化 | 抽屉 tab 展示数与账号归属（学生/教师/管理）易错 | P1 |
| R8 | 三端功能缺乏系统化回归基线 | 细节 bug（文案/布局/数量/跳转）易复发、回归靠人肉 | **P0**（质量护栏） |

> **核心结论**：根因不是某个页面的小 bug，而是**缺少「课程作用域」「掌握度分级」「统计口径」三个数据的单一事实源（source of truth）**，叠加**种子 DB 未随代码重建**、**登录演示账号列表缺滚动容器**、**全链路回归基线缺失**。方案第一要务是统一模型 + 统一函数 + 固化回归用例，再谈功能与数据。

## 2. 问题总览与分级

### 2.1 缺陷清单（分级 / 证据）

#### R1 · 课程作用域无单一事实源【P0】
现状存在 **3 套互相独立的课程取值逻辑**：
- 学情接口：`src/app/api/student/profile/route.ts:40-42` 按 `course.class_id = student.class_id` 取本班课程。
- 作业/材料/讨论区：`src/lib/course-access.ts:29-41` `getAccessibleCourseIds()` 按 `course.class_id = authUser.classId`。
- 知识图谱：`src/app/api/student/knowledge-graph/route.ts:225` 用 `canAccessCourse()` 逐课程校验。

三处底层逻辑相同（都按班级过滤），但 **数据源字段不同**：`student.class_id`（DB）vs `authUser.classId`（会话/演示账号）。当演示账号的 `classId` 与 DB 学生 `class_id` 不一致、或 DB 是 `org.ts` 新种子之前的旧数据时，两接口就会返回不同课程集 —— 表现为「学情4门 / 作业2门」。

**证据**：种子 `src/storage/database/seed/org.ts:14-23` 每个班级明确只配 **2 门课**；截图软工2501学生却显示 Python/数据结构/数据库/操作系统 **4 门**（恰为两班并集）→ 判断为 **旧 DB 未按当前种子重建**，叠加会话 classId 与 DB 不一致所致。

#### R2 · 掌握度 / 薄弱 / 统计口径破碎【P0】
同一页内存在 **至少 4 套阈值/口径**：
| 位置 | 逻辑 | 薄弱口径 |
|------|------|---------|
| `profile/route.ts:351-354` `knowledgeStats` | 已学点 `>=80`=精通；`<70`=薄弱 | **<70**，且 `basic` 写成 `<60`（命名与语义错位） |
| `profile/route.ts:391-403` `masteryTiers` | `mastered>=\80 / good>=60 / weak>=30 / none` | **30–60** |
| `profile/route.ts:222` 课程弱项 | `x.rate < 70` | **<70** |
| 领域统一层 `src/lib/domain.ts` `classifyMastery` | `null/<30` 未学；`<60` 薄弱；`<80` 基本；`\>=80` 掌握 | **<60** |

**矛盾即源于此**：顶部「100知识点 · 4薄弱」来自 `masteryTiers`（只统计有掌握度且 30–60 的）；底部「薄弱86个」来自把「未学(82)+弱(4)」当薄弱或用了 `<70`。**同一指标、四种算法** → 用户看到自相矛盾的数字。

#### R3 · 知识图谱筛选只改画布、不改统计【P1】
`src/app/student/knowledge-graph/page.tsx:194-214`：`filter`（all/weak/unlearned/mastered）只计算 `keep` 集合并对非命中分支加 `.kg-dim` 降暗；**顶部综合掌握率与左侧图例的 `mastered/weak/unlearned` 计数仍读后端固定的 `graphData.masteryStats`**。于是切换筛选后，图形变暗但「数值」不动 → 用户感觉「只有中间能改、其他值不变」。

#### R4 · 错题本 ↔ 图谱 ↔ 掌握度无双向联动【P1】
`errorBook`（`schema.ts:248-260`）字段完整——含 `student_id / knowledge_point_id / assignment_id / exam_id / review_status / review_count`，数据基础足够。但：
- 错题本前端页与知识图谱页**彼此无跳转、无定位参数**（无 `?kp=` / 选中态互通）。
- 图谱节点掌握度来自 `knowledgeMasteryLog` > `gradingTask`（`knowledge-graph/route.ts:243-299`），与错题本的 `review_status`（已改/待改）**未做任何交叉高亮**。

#### R5 · 种子数据陈旧且关联不自洽【P0】
已有模块化种子：`org.ts`（组织/用户/课程）、`knowledge.ts`（知识点）、`questions.ts`、`assignments.ts`、`exams.ts`、`social.ts`。问题：
- 当前 `data/racinglight.db` 与 `org.ts` 的「每班2门」定义不符 → **DB 未随种子代码重建**。
- 知识点↔课程、错题↔知识点、掌握度↔知识点三类关联**无法保证彼此自洽**（无生成期对账），导致 R2 的数字矛盾被写死进数据。

#### R6 · 登录抽屉演示账号列表不可滚动【P1】
证据：`src/app/login`（即 `src/app/page.tsx:347-384`）的“切换用户”抽屉里静态渲染全部 20 名学生 `DEMO_STUDENTS` 与 2 名教师、1 名管理员。`SheetContent` 基座已带 `overflow-y-auto`（`src/components/ui/sheet.tsx:61`），但页面在 `SheetContent` 内又包了一层 `<div className="mt-6 space-y-1">`（`page.tsx:351`）作为列表容器；当列表项足够多、容器在**固定高度抽屉**内铺满时，滚动被外层 `flex flex-col` 拉伸吞掉/视觉上卡住 → 用户无法下滑看到 `stu_1_9 许雪` 等靠后账号。

**修复方向（Phase UX-1）**：为 `page.tsx` 内 `SheetContent` 增加显式 `overflow-y-auto` + `flex-1` + 列表容器 `max-h` 约束，或直接让列表容器自身 `overflow-y-auto`；保证任意角色台账都能完整滚动到底。

#### R7 · 演示账号口径冒烟未固化【P1】
证据：`page.tsx:20-49` 定义 `DEMO_ADMIN / DEMO_TEACHERS / DEMO_STUDENTS`，`page.tsx:52-56` `demoOfRole()`、`page.tsx:165-170` `filterUsers`。历史曾发生“学生 tab 误渲染教师账号”，说明【前端常量 ↔ 种子账号 → 后端登录鉴权】的口径没有一条自动冒烟校验线。学生/教师/管理三层 tab 分别展示 `20 / 2 / 1` 个账号（`page.tsx:343`），一旦种子改动或常量未同步即隐性出错。

**修复方向（Phase UX-2）**：把账号台账抽成单一数据源（`src/lib/demo-accounts.ts`，seed 直接以其为准生成账号），并新增一条**自动化冒烟**：断言 3 个角色 tab 的展示数与账号可达性、密码规则（管理员固定 `123456`，学生/教师默认密码 = 用户名）三者一致。

#### R8 · 三端功能缺乏系统化回归基线【P0（质量护栏）】
现状：缺陷大多靠用户零星反馈暴露；修复后无固化用例，`tsc`/`build` 只查编译不查行为。学生端（学情/作业/考试/图谱/错题/讨论/助手/材料）、教师端（看板/作业/考试/批改/题库/公告/成绩）、管理端（组织/课程/用户）缺少一份**可复跑的端到端冒烟清单**。

**修复方向（Phase QA）**：建立“一次登录–选课–答题–批改–公布–学情/图谱/错题–申诉/退回 幂等”的**全链路回归用例**（挂在 `docs/` 或 `scripts/`），每次发版前按清单人工冒烟并通过 `tsc --noEmit` + `build.bat` 双门禁。

## 3. 根因分析（Why）

```
根因 = 三个「单一事实源」缺失 + 一次「陈旧DB未重建」+ 一处「UI滚动容器缺失」+ 一项「回归基线缺失」
   │
   ├─ ① 课程作用域：student.class_id(DB) 与 authUser.classId(会话) 无统一入口 → R1
   ├─ ② 掌握度分级：domain.ts 已建，但 5 处业务代码仍各写阈值 → R2
   ├─ ③ 统计口径：图谱统计 = 静态后端字段，不随前端筛选计算 → R3
   ├─ ④ 业务联动：错题/掌握度/图谱三表无统一的“按知识点寻址”API → R4
   ├─ ⑤ 数据一致性：种子生成 ≠ DB 实际，且无对账断言 → R5
   ├─ ⑥ UI 滚动：抽屉列表容器未做“撑开可滚”约束 → R6
   ├─ ⑦ 演示账号台账：前端常量与种子账号缺冒烟实体 → R7
   └─ ⑧ 质量反馈回路：无端到端回归基线，修复行为不固化 → R8
```

## 4. 整改目标架构

### 4.1 建立「单一事实源」三件套（前置，Phase 0）

**① 课程作用域统一函数**（收敛 R1）
- 新增 `resolveStudentCourses(studentId, classId)`，**唯一** SQL 入口，供所有学生端接口复用。
- 定义：**“学生本学期课程 = 其班级绑定的全部课程”**，且以 **DB 行 `user.class_id` 为准**；会话 `authUser.classId` 仅作缓存，校验不一致时以 DB 覆盖。
- 接入点：`profile`、`assignments`、`materials`、`knowledge-graph`、`courses`、`error-book`、`discussion` 全部改为调用该函数，**删除各自的内联查询**。

**② 掌握度分级统一**（收敛 R2）
- `src/lib/domain.ts` 已是最低标准（`null/<30` 未学、`<60` 薄弱、`<80` 基本、`>=80` 掌握）。
- **强制所有写阈值处改引用** `classifyMastery / isWeakMastery / MASTERY_*`，含但不限于：
  - `profile/route.ts:222`（`<70`）
  - `profile/route.ts:351-354`（`knowledgeStats` 的 `<70`、`<60` 错位）
  - `profile/route.ts:391-403`（`masteryTiers` 三段）
  - Kotlin/前端其他任何硬编码 `>=80 / <70 / <60`。

**③ 统计口径统一**（收敛 R3）
- 定义 **“掌握率金字塔”** 唯一结构 `MasteryTierCount = { total, mastered, good, weak, unlearned }`，作为**前端唯一渲染源**。
- **该结构必须支持按任意节点子集重算**（前端动态计算），图谱顶部与图例共享同一计算函数，杜绝「静态统计 vs 动态图」不一致。

### 4.2 后端 API 收敛建议

- 抽出公共 `src/lib/course-scope.ts` 与 `src/lib/mastery-stats.ts`，避免各 route 重复 SQL。
- 为「错题 ↔ 知识点」新增**按知识点寻址**能力：`error-book?kp_id=&course_id=` 与 `knowledge-graph?focus_kp=&course_id=`，统一 URL 契约，供双端互跳。

### 4.3 数据一致性对账（防 R5 复发）

种子生成结束时**强制断言**（自动化，任何一条失败即判种子失败）：
1. 每门课程都归属且仅归属一个班级；每班课程数 = 规划数（2）。
2. 每个知识点 `course_id` 落在其课程可访问班级内。
3. 每条错题 `knowledge_point_id` 存在且归属该生课程。
4. 每条掌握度日志 `knowledge_point_id` 存在。
5. 该生课程总数在 profile/assignments/knowledge-graph/courses 四接口**完全一致**。

## 5. 分模块整改方案

### 5.1 R1 · 课程数量一致性（学情 vs 作业）
- 实施：替换为统一 `resolveStudentCourses`；并**重建种子**（见 5.5），使 DB 与 `org.ts` 的「软工2501=2门」一致。
- 验收：田斌（软工2501）「我的学情」与「作业」课程筛选 tab **均为且仅为**：数据库原理与应用、操作系统原理；总数=2。
- 风险：低。纯收敛查询入口，不改语义。

### 5.2 R2 · 掌握度/薄弱统一
- 实施：`knowledgeStats`、`masteryTiers`、`courseData.weakKps` 统一改引用 `classifyMastery`；修正 `basic` 语义（应指 60–79 良好段，而非 `<60`）。
- 验收：顶部企业卡与底部统计卡「薄弱」数字一致；任意单科筛选下四段之和 = 该课总知识点数。
- 风险：中（涉及前端字段消费）。需同步核对 overview 页消费的字段名。

### 5.3 R3 · 知识图谱筛选联动统计
- 实施（`knowledge-graph/page.tsx`）：
  1. 将 `masteryStats`/图例计数/顶部掌握率从 `graphData` 静态字段 → **基于当前 `filter` 与当前课程动态重算**。
  2. 顶层任务卡片工具条增加“仅统计命中子集”切换，实时反映「当前筛选命中知识点/错题数」。
  3. 空结果态：命中集合为空时显示友好提示而非全暗。
- 验收：切到「只看薄弱」时，图例「薄弱=N」与顶部掌握率按命中集合重算，其他段置灰为 0 或隐藏。
- 风险：中。改动集中在单一页面，需同步 d3 局部更新（enter/update/exit）避免重载。

### 5.4 R4 · 错题本 ↔ 图谱 ↔ 掌握度双向联动
- 实施：
  1. 图谱节点追加「错题角标」：该知识点命中错题本且未订正（`review_status != mastered`）时描红/加徽标。
  2. 顶部/详情抽屉新增「去错题本」「看该知识点错题」入口 → 携带 `?course_id=&kp_id=` 跳转错题本并自动锚定。
  3. 错题本每条错题新增「在图谱中定位」→ 回跳知识点图谱并 `focus_kp` 自动聚焦、展开路径。
- 验收：从错题本点一条错题 → 图谱自动聚焦该叶子并高亮其掌握度；反向亦然。跨页状态经 URL 参数可靠恢复。
- 风险：中。核心是**统一 URL 寻址契约**，建议先定契约再落地两页。

### 5.5 R5 · 种子数据重建（确定性、自洽）
- 原则：**固定 RNG 种子**，每次重建产出完全一致、可回归的数据。
- 关键口径（写死并经断言）：
  - 2 班 × 10 生 = 20 生；2 教师（各 1 班、2 门课）；1 管理员。
  - 每班 2 门课程；**每门课 6 个作业**（2 待作答 / 2 待批改 / 2 已批改公布），修"每课6个只显示4个"的展示回归。
  - 每门课知识点总数固定（如 25/课 → 100 知识点总池），且知识点↔课程↔掌握度↔错题 **四表对账一致**。
- 部署：`setup.bat` 流程中**先清库 `data/racinglight.db` 再全量重建**，彻底消除“旧 DB 与种子定义不符”。
- 验收：重跑 seed 后跑 4.3 的全部断言绿色；清空旧库下限为 `data/racinglight.db` 即可复位（符合既有约定）。

### 5.6 R6 · 登录抽屉演示账号列表可滚动
- 实施（`page.tsx:347-384`）：为 `SheetContent` 追加 `overflow-y-auto` 与 `flex-1 min-h-0`，列表容器 `<div className="mt-6 space-y-1">` 改为 `overflow-y-auto pr-1`；必要时给抽屉设 `max-h-[80vh]`，确保 3 角色台账完整下滑。
- 验收：学生 tab 可从 `stu_0_0` 一路滚滚到底到 `stu_1_9`；教师/管理 tab 分别可见 2/1 条。
- 风险：低。纯样式约束，不影响逻辑。

### 5.7 R7 · 演示账号台账单一化 + 冒烟
- 实施：
  1. 抽 `src/lib/demo-accounts.ts` 为唯一台账（`DEMO_ADMIN / DEMO_TEACHERS / DEMO_STUDENTS / demoOfRole`），`page.tsx` 改引用，seed 账号生成以同源为准。
  2. 新增冒烟断言：每角色 tab 展示数 = 台账数；学生/教师密码=用户名、管理密码=`123456`；账号可真实登录。
- 验收：改台账后抽屉计数与登录可达性同步，无“学生 tab 出现教师账号”类回归。
- 风险：中。抽常量需同步 seed 与前端两侧引用。

### 5.8 R8 · 全量功能回归基线（三端）
- 实施：在 `docs/` 新建**回归测试清单**（按学生/教师/管理三端、按核心链路线列出操作与预期断言），覆盖：登录（3角色）→ 选课 → 作业/考试答题 → 批改公布 → 学情/图谱/错题/讨论 → 申诉/退回幂等。每次发版执行并把结果回填。
- 验收：发版前置 확인 `tsc --noEmit` 0 错 + `build.bat` 通过 + 清单逐项勾选无遗留。
- 风险：低。纯流程规范 + 文档化。

## 6. 验收测试计划

### 6.1 静态质量
- `tsc --noEmit` 全项目 **0 错误**。
- `build.bat` 生产构建通过。

### 6.2 数据一致性（自动化断言脚本）
执行 4.3 五条断言；四接口课程集一致。

### 6.3 三端冒烟（学生/教师/管理）
| 用例 | 预计结果 |
|------|---------|
| 学生「我的学情」课程数 | = 本班课程数（2） |
| 学生「作业」课程数 | = 本班课程数（2），且每课 6 个作业齐全 |

## 8. 企业级规范建议（长期）

1. **单一事实源**：阈值、单位、时区、课程作用域、演示账号台账一律收敛到 `src/lib/*`，业务代码禁止散落魔数。
2. **幂等可重放**：掌握度/错题写入须幂等（重放不叠加），统一 UTC。
3. **API 契约化**：课程/知识点/错题寻址使用稳定 URL 参数，支持深链与刷新恢复。
4. **自动对账**：种子与迁移结束均跑一致性断言，CI 卡壳。
5. **可观测**：关键聚合接口（profile/knowledge-graph）加耗时日志与指标，防 N+1 与慢查询。
6. **回归基线**：发版前必须跑 6.4 全链路回归清单 + `tsc` 0 错 + `build.bat` 通过，行为变更可审计。
7. **最小改动**：本次聚焦 R1–R8，不借机做大重构，降低回归面。
