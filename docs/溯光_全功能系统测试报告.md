# 溯光 TracingLight · 全功能系统测试报告

> 版本：v1.0　|　测试日期：2026-09-04　|　测试方式：静态代码审查 + 接口实测（curl）
> 覆盖范围：40 个 API、四端页面（教师/学生/管理）、数据层、认证体系

---

## 一、测试结论（TL;DR）

系统功能主链路（登录→作业→批改→学情→推荐）可运行，但存在**一批系统性的安全漏洞**，集中在「学生端 API 的越权访问（IDOR）」和「个别接口完全无鉴权」。**上线前必须修复，答辩现场若被评委实测到，属严重扣分项。**

**共发现缺陷 20 项：P0 严重 4 项、P1 高 7 项、P2 中 6 项、P3 低 3 项。**

| 严重度 | 数量 | 说明 |
|:---:|:---:|------|
| 🔴 P0 | 4 | 数据泄露 / 未授权篡改 / 越权写入，可被直接利用 |
| 🟠 P1 | 7 | 越权读取群、无鉴权接口、N+1 性能、内存库风险 |
| 🟡 P2 | 6 | 角色校验缺失、逻辑边界、暴力破解、兼容性 |
| 🟢 P3 | 3 | UX 细节 |

---

## 二、严重程度分级标准

| 级别 | 定义 |
|------|------|
| **P0 严重** | 可被未授权利用，导致数据泄露/篡改/越权写入，或核心功能不可用 |
| **P1 高** | 越权读取敏感数据、性能瓶颈、架构级技术债 |
| **P2 中** | 角色校验缺失、边界处理不当、安全加固缺失 |
| **P3 低** | 体验细节、非阻断性瑕疵 |

## 三、缺陷清单

### 🔴 P0 严重（4 项）

#### P0-1　学生可替他人提交/覆盖作业（IDOR 写入）
- **位置**：`src/app/api/student/assignments/submit/route.ts`
- **表现**：接口从请求体读取 `student_id`，只校验了「角色是 student」，**未校验 `student_id === 当前登录用户`**。
- **触发条件**：学生 A 登录后，携带他人 `student_id` 调用提交接口。
- **影响**：任意学生可篡改/覆盖任意其他学生的作业答案（delete 旧答案 + insert 新答案），破坏成绩真实性。
- **证据**：代码 `const { assignment_id, student_id, answers } = body`，后续 `eq(answer.student_id, student_id)` 直接用入参。

#### P0-2　错题状态修改接口完全无鉴权
- **位置**：`src/app/api/student/errors/route.ts` 的 `PATCH`
- **表现**：`PATCH` 方法**没有任何 `requireAuth`**，直接按 `error_id` 更新 `review_status`。
- **触发条件**：未登录，直接 `PATCH /api/student/errors`。
- **影响**：任意人（含未登录）可把任意学生的错题标记为「已掌握」等，篡改学习数据。
- **实测**：`curl -X PATCH ... {"error_id":1,"review_status":"mastered"}` → 返回 `{"success":true}`。

#### P0-3　错题列表未传学生ID即泄露全量数据
- **位置**：`src/app/api/student/errors/route.ts` 的 `GET`
- **表现**：`student_id` 为可选参数，**不传则返回全表错题**（无兜底到当前用户）。
- **触发条件**：任意学生登录后，不带 `student_id` 访问。
- **影响**：学生可看到**全体学生的错题**（含他人作答内容、错因）。全库 211 条错题，张同学本人仅 19 条，但接口返回 211 条。
- **实测**：`stu_zhang` 不带参访问 → 返回 211 条（全体）。

#### P0-4　错题接口可越权读取他人数据（IDOR 读）
- **位置**：`src/app/api/student/errors/route.ts` 的 `GET`
- **表现**：即使传了 `student_id`，也不校验是否等于当前用户，可指定任意学生ID。
- **触发条件**：学生 A 传 `student_id=B`。
- **影响**：读取任意学生错题详情（含作答、错因、知识点）。

> 注：P0-3 与 P0-4 同源，均因 `student_id` 未绑定 `user.userId`。

---

### 🟠 P1 高（7 项）

#### P1-1　学生端越权读取群（8 个接口 IDOR）
- **位置**：`profile`、`recommend`、`schedule`(GET)、`knowledge-graph`、`study-plan`、`study-plan/generate`、`assignments`、`assignments/[id]`
- **表现**：上述接口均从查询参数或请求体读 `student_id`，未校验与登录用户一致。
- **影响**：学生可读取任意同学的**成绩、掌握度、薄弱点、学习规划、课表、作业、推荐**等全部学习数据。
- **实测**：`stu_zhang` 访问 `profile?student_id=4` → 成功返回「李同学」学情；`schedule?student_id=4` → 返回李同学课表。

#### P1-2　能力/思政图谱接口完全无鉴权
- **位置**：`src/app/api/student/triple-graph/route.ts`
- **表现**：`GET` 无 `requireAuth`，未登录即可访问。
- **实测**：未登录访问 → 返回 4 个能力点 + 关联知识点。
- **影响**：图谱数据（含课程结构、能力/思政映射）无授权泄露。

#### P1-3　学生课表接口可越权写入
- **位置**：`src/app/api/student/schedule/route.ts` 的 `POST`
- **表现**：请求体 `student_id` 未校验，可替他人新增/修改课表。
- **影响**：越权篡改他人课表安排。

#### P1-4　SQLite 用 sql.js 内存库，进程崩溃即丢数据
- **位置**：`src/storage/database/db.ts`
- **表现**：`sql.js` 将整库载入内存，`saveDb()` 手动全量序列化导出（当前 944KB）。
- **影响**：① 进程崩溃/断电丢失未落盘写入；② 高频写触发全量序列化，性能差；③ 并发写不安全。这是此前已识别的「必须返工」架构债，仍未迁移 better-sqlite3。

#### P1-5　学情接口 N+1 查询
- **位置**：`src/app/api/student/profile/route.ts`（薄弱知识点循环内）
- **表现**：`realWeakKps.map` 内对每个薄弱知识点单独 `db.select().from(knowledgePoint)` 查名称（TOP10 = 10 次额外查询）。
- **影响**：随薄弱点数量线性增加查询次数，数据量大时响应变慢。

#### P1-6　教师课程接口无角色限制
- **位置**：`src/app/api/teacher/courses/route.ts`
- **表现**：`requireAuth(request)` **未指定 `requiredRole`**，任何登录用户（含学生）可调用；且返回**全部课程**而非当前教师课程。
- **影响**：学生可调用教师接口；教师之间课程数据不隔离。

#### P1-7　登录无暴力破解防护
- **位置**：`src/app/api/auth/login/route.ts`
- **表现**：仅做用户名+密码比对，**无速率限制、无验证码、无失败锁定**。
- **影响**：可被暴力枚举密码（演示账号密码=用户名，风险更高）。

---

### 🟡 P2 中（6 项）

#### P2-1　提交作业不校验题目归属
- **位置**：`submit/route.ts`
- **表现**：`answers` 里的 `question_id` 未校验是否属于该 `assignment_id`。
- **影响**：可提交作业不存在的题目答案，产生脏数据。

#### P2-2　错题状态值无合法性校验
- **位置**：`errors/route.ts` 的 `PATCH`
- **表现**：`review_status` 可传任意字符串，无枚举白名单。
- **影响**：数据被写入非法状态值，污染统计。

#### P2-3　JWT 密钥使用示例默认值
- **位置**：`.env.example` 中 `JWT_SECRET=change_this_to_a_random_secret_string`
- **表现**：若实际 `.env` 未改，则 Token 可被伪造。
- **影响**：认证体系失效风险。**需确认实际部署是否已替换。**

#### P2-4　图谱接口全量加载后内存过滤
- **位置**：`triple-graph/route.ts`
- **表现**：`abilityKnowledge`/`ideologyKnowledge` 全量 `.all()` 后在前端 `filter` 关联。
- **影响**：关联数据量大时内存/耗时上升（当前数据量小不敏感，属潜在问题）。

#### P2-5　通知接口无角色限定
- **位置**：`notifications/route.ts`
- **表现**：`requireAuth(request)` 无 `requiredRole`，但按 `userId` 过滤，暂无明显越权，属冗余校验缺失。

#### P2-6　sql.js WASM 兼容性
- **表现**：WASM 模块加载在低端设备/受限浏览器（如禁用 WASM）下可能失败或慢。
- **影响**：兼容性隐患，答辩演示若换设备需注意。

---

### 🟢 P3 低（3 项）

- **P3-1**：部分页面 loading/空状态/错误提示风格不统一（如骨架屏、错误文案差异）。
- **P3-2**：`student/profile` 中 `radarData`/`trendData`/`errorData`/`courseComparison` 仍来自 mock 数据，与真实数据口径并存，答辩可能被追问「数据来源」。
- **P3-3**：接口错误信息部分直接透传 `error.message`，可能泄露内部实现细节。

## 五、修复优先级建议

### 第一批（P0，答辩前必做，工作量约 1~2 天）
统一方案：**所有学生端接口改用 `authUser.userId` 作为数据归属，废弃前端传入的 `student_id`**（或至少强制校验 `student_id === user.userId`）。

1. `student/errors` GET/PATCH：绑定 `userId`；PATCH 补 `requireAuth`；
2. `student/assignments/submit`：`student_id` 强制等于 `userId`；
3. `student/errors` GET：不传 `student_id` 时默认当前用户，绝不返回全表；
4. `student/triple-graph`：补 `requireAuth`。

### 第二批（P1，本周）
5. 8 个 IDOR 接口统一改为 `userId` 归属；
6. `teacher/courses`：加 `requiredRole='teacher'` 并按 `teacher_id` 过滤；
7. 登录加基础速率限制（内存计数即可）；
8. 启动 better-sqlite3 迁移（或至少在文档明确「演示模式可接受」）；
9. 消除 profile 的 N+1（一次 `inArray` 批量查知识点名）。

### 第三批（P2/P3，锦上添花）
10. 提交校验 question_id 归属；错题状态白名单校验；
11. 替换 JWT_SECRET；图谱关联改 SQL join；
12. mock 数据全面真实化；错误信息脱敏。
